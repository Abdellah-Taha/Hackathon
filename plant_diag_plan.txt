PLANTCARE AI
PROJECT ROADMAP AND TEAM EXECUTION PLAN
=======================================

Project: Plant image diagnosis and care assistant
Team: 4 people — 2 AI/backend, 2 web frontend
Goal: Build a hackathon-ready web app that turns a plant photo into an evidence-aware health report and practical care recommendations.

1. PRODUCT DEFINITION
---------------------

The app lets a user upload a photo of a plant and receive a concise report about its visible condition, possible health issues, confidence/uncertainty, and suggested next steps.

Core user journey:
1. The user uploads a clear image of a leaf or whole plant.
2. The user may provide optional context: plant name if known, region/location, growth stage, and symptoms they have noticed.
3. The AI analyzes the image and identifies observable symptoms.
4. The system returns one or more plausible explanations, not an unjustifiably certain diagnosis.
5. The app presents a readable report with recommended actions, things to monitor, limitations, and optional follow-up questions.
6. Later, the user may ask follow-up questions about the report.

The AI must have a clear, substantive role. It should inspect the image, extract visual evidence, compare plausible explanations, and generate a structured report. It must not merely fill a generic template with text.

MVP — BUILD NOW:
- Image upload and preview.
- Image validation and basic error handling.
- AI-powered visual symptom analysis.
- Structured plant health report.
- Possible causes with confidence/uncertainty.
- Prioritized, practical care recommendations.
- Explicit limitations when the photo is unclear or evidence is insufficient.
- End-to-end frontend/backend integration.

OPTIONAL STRETCH FEATURES — ONLY AFTER THE MVP WORKS:
- Plant species suggestion.
- Follow-up chat grounded in the generated report.
- Basic seasonal context.
- Weather API integration.
- Report export to PDF.

POST-HACKATHON FEATURES:
- User accounts and diagnosis history.
- Repeated image tracking over time.
- Larger crop- or plant-specific knowledge base.
- Offline/mobile app.
- Expert or community features.

Do not attempt to build every feature during the hackathon. Prove the main workflow first.

2. RECOMMENDED AI PIPELINE
--------------------------

Step 1 — Input validation
- Check file type, file size, image readability, and whether the image plausibly contains a plant.
- Return a useful error for invalid, unreadable, or unsupported images.

Step 2 — Visual analysis
- Use a vision-capable model/API or a dedicated plant-disease image classifier.
- First identify observable symptoms: yellowing, spots, wilting, discoloration, mildew-like growth, pest traces, leaf damage, or other visible features.
- Distinguish observations from conclusions. For example, “yellowing around the leaf edge” is an observation; “nutrient deficiency” is a possible explanation.

Step 3 — Diagnosis hypotheses
- Produce up to 1–3 plausible explanations when supported by the image.
- Include confidence/uncertainty and the visual evidence behind each explanation.
- Do not force a diagnosis when the evidence is weak.
- If image quality is poor or important context is missing, ask for another image or a follow-up detail.

Step 4 — Context enrichment
- Use the plant name, region, growth stage, and user-provided symptoms as context when available.
- Do not treat context as proof of a diagnosis.

Step 5 — Recommendations
- Prioritize low-risk, actionable steps.
- Explain why each action may help.
- Include what to monitor and what additional information would improve the assessment.
- Recommend expert/local agricultural advice when the issue may be serious or uncertain.

Step 6 — Structured output and validation
- Return JSON conforming to the agreed report schema.
- Validate required fields and allowed values before returning the response to the frontend.
- Handle model/API failures, malformed outputs, timeouts, and rate limits.

MODEL CHOICE:
For a short hackathon, a vision-capable model API is likely the fastest way to create an end-to-end demo, if the event rules allow it and the team has access. Check image support, pricing, rate limits, privacy, and terms.
A dedicated classifier can be more constrained and measurable, but requires dataset selection, preprocessing, and evaluation. Do not train a custom model from scratch during the hackathon unless there is already a suitable model and dataset.
Keep provider-specific code behind a small interface so the model can be changed without rewriting the frontend.

3. REPORT JSON CONTRACT
-----------------------

Use one shared schema for the backend and frontend. The following is a conceptual example; keep field names consistent across the entire codebase.

{
  "plant_name": "unknown or best-supported identification",
  "overall_status": "healthy | monitor | concern | urgent",
  "observations": [
    {
      "symptom": "yellowing near leaf edge",
      "location": "lower leaf",
      "evidence": "visible in the uploaded image"
    }
  ],
  "possible_causes": [
    {
      "name": "possible nutrient stress",
      "confidence": "low | medium | high",
      "reason": "brief explanation grounded in the image"
    }
  ],
  "severity": "low | moderate | high | uncertain",
  "recommended_actions": [
    {
      "priority": 1,
      "action": "specific action",
      "reason": "why this action may help"
    }
  ],
  "seasonal_context": "general context, if supported",
  "what_to_monitor": ["specific signs to watch"],
  "limitations": ["what cannot be determined from this image"],
  "follow_up_questions": ["useful question, if needed"]
}

Important:
- Treat the JSON above as a starting contract, not a requirement to invent values.
- Use explicit unknown/uncertain values when necessary.
- Do not present a possible cause as a confirmed diagnosis.
- The frontend should render the returned data, not rely on hard-coded demo text.

4. SEASONAL CONTEXT AND FUTURE WEATHER INTEGRATION
--------------------------------------------------

A season label alone is not very useful. Seasonal guidance should depend on plant type and region and must be labelled as general context when it is not based on specific evidence.

For a later weather feature:
1. Ask the user for a location or request permission to use approximate location.
2. Call a real weather API.
3. Extract only relevant weather signals.
4. Provide those values to the recommendation step as context.
5. Explain how weather may affect care; do not claim weather proves the cause of a disease.

Potentially relevant weather signals:
- Recent and forecast rainfall: watering decisions and prolonged leaf-wetness risk.
- Temperature highs and lows: possible heat or cold stress.
- Humidity: possible fungal-pressure context, without claiming that a fungal disease is confirmed.
- Wind and extreme weather: plant protection and timing of outdoor care.

For the MVP, seasonality can be a short context section based on plant type and user-entered region. Do not fabricate current weather or imply that location-specific weather has been fetched if no API was called.

5. TEAM RESPONSIBILITIES
------------------------

AI TEAMMATE 1 — VISION AND DIAGNOSIS
Responsibilities:
- Select and test the vision model/API or classifier.
- Implement image analysis and symptom extraction.
- Produce plausible causes, confidence/uncertainty, and image-grounded reasoning.
- Test with varied plant photos and tune prompts/model settings.
Deliverables:
- Working image-analysis module.
- Example input/output cases.
- Documented limitations and model choice.

AI TEAMMATE 2 — BACKEND AND ORCHESTRATION
Responsibilities:
- Define and implement the diagnosis endpoint.
- Connect image analysis to report generation.
- Validate the report against the shared JSON schema.
- Handle errors, timeouts, malformed model responses, and rate limits.
- Keep provider-specific code isolated behind a simple interface.
Deliverables:
- Working backend endpoint.
- Schema validation.
- Error responses and example JSON.
- Integration instructions for the frontend.

WEB TEAMMATE 1 — UPLOAD FLOW AND USER EXPERIENCE
Responsibilities:
- Build the main page and upload experience.
- Add image preview and optional context fields.
- Implement loading, invalid-image, error, and retry states.
- Ensure the interface works on common screen sizes.
Deliverables:
- Working upload page.
- Context form.
- Loading and error states.

WEB TEAMMATE 2 — REPORT UI AND INTEGRATION
Responsibilities:
- Build the report layout and visual hierarchy.
- Connect the frontend to the backend endpoint.
- Render observations, possible causes, confidence, recommendations, and limitations.
- Handle missing or uncertain fields gracefully.
- Polish the end-to-end demo.
Deliverables:
- Report components.
- API integration.
- End-to-end test results.
- Demo-ready interface.

TEAM WORKING AGREEMENT:
- Agree on the API request/response contract before implementing separate components.
- The AI/backend team should provide a mock endpoint or fixed JSON fixture early.
- The web team should build against mock data before the real model is ready.
- Use one shared repository and short feature branches.
- Assign a clear owner for integration and the final demo.
- Test the complete workflow early; do not wait for the AI to be perfect.

6. API CONTRACT
----------------

Suggested endpoint:
POST /api/diagnose

Request:
- Content type: multipart/form-data.
- Required: image.
- Optional: plant_name, region, growth_stage, user_observed_symptoms.

Response:
- JSON matching the agreed report schema.

Handle these cases explicitly:
- Unsupported file type.
- File too large.
- Unreadable or invalid image.
- No plant visible or image outside the intended use.
- Low-confidence analysis.
- Model/API unavailable or timed out.
- Invalid model output.
- Rate limit exceeded.

The frontend and backend must agree on field names and value types. Document the contract in the repository so both pairs can work independently.

DEFINITION OF DONE FOR INTEGRATION:
- The frontend uploads an image and receives a real backend response.
- The report renders backend fields rather than static sample text.
- Missing and uncertain information is handled explicitly.
- Loading, failure, invalid-image, and retry states work.
- At least five varied images have been tested: a healthy plant, visible symptoms, poor-quality image, non-plant image, and an ambiguous case.

7. EXECUTION ROADMAP
--------------------

PHASE 0 — ALIGNMENT (FIRST 30–45 MINUTES)
AI pair:
- Choose the model approach.
- Agree on observations vs. hypotheses and uncertainty rules.
- Define the report schema.
Web pair:
- Agree on the user flow and report layout.
- Create the app/repository skeleton.
Exit criterion:
- One agreed MVP and one shared request/response contract.

PHASE 1 — SKELETON (NEXT 45–60 MINUTES)
AI pair:
- Create the /api/diagnose endpoint with a mocked JSON response.
- Start connecting the selected model/API.
Web pair:
- Build the upload form, loading state, and report UI using mock data.
Exit criterion:
- The frontend can display a complete mocked report.

PHASE 2 — CORE AI (NEXT 1–2 HOURS)
AI pair:
- Implement image analysis.
- Generate structured output.
- Validate output and handle failures.
Web pair:
- Connect to the real endpoint.
- Handle loading, errors, and missing fields.
Exit criterion:
- A real uploaded image flows through the AI/backend and produces a report in the UI.

PHASE 3 — QUALITY (NEXT APPROXIMATELY 1 HOUR)
AI pair:
- Test varied images.
- Improve prompts/model settings.
- Prevent unsupported certainty and risky recommendations.
Web pair:
- Improve readability, responsive layout, preview, and error states.
Exit criterion:
- The app works reliably across several test cases.

PHASE 4 — POLISH AND PITCH (FINAL 45–60 MINUTES)
AI pair:
- Prepare one strong example.
- Explain the model, AI pipeline, and limitations.
Web pair:
- Polish the visual hierarchy.
- Check every button and state.
- Rehearse the demo.
Exit criterion:
- A reliable 2–3 minute demo and a clear explanation of the problem, solution, AI role, and impact.

Adjust phase lengths to the actual hackathon schedule. Prioritize the end-to-end flow over optional features.

8. QUALITY, SAFETY, AND CREDIBILITY
------------------------------------

- Say “possible cause” rather than presenting a photo-based guess as confirmed.
- Show the visible observations that support the model's conclusions.
- If confidence is low or the image is poor, ask for another photo or more context.
- Avoid recommending pesticides, chemical concentrations, or irreversible actions based only on an image.
- Prefer low-risk care steps and recommend local expert advice for serious or unclear cases.
- Do not claim weather caused a disease; use it only as a contextual risk factor.
- Protect uploaded images. Avoid retaining them by default and explain if images are sent to an external model provider.
- Do not fabricate plant identity, seasonality, weather, or confidence values.
- Evaluate the system on more than one ideal example.

9. DEMO SCRIPT AND JUDGING NARRATIVE
------------------------------------

1. Problem: Plant owners notice symptoms but do not know what they mean or what to do next.
2. Action: Upload a plant photo and optionally provide the plant type or region.
3. AI moment: Show image-grounded observations, plausible causes, confidence/uncertainty, and explanations.
4. Useful outcome: Show prioritized care actions and what signs to monitor, rather than only a disease label.
5. Future direction: Explain how local weather data could help adapt recommendations to upcoming heat, rain, or humidity.

Make the AI contribution visible during the demo. A report containing only generic plant facts will not convincingly demonstrate image diagnosis.

10. FEATURES TO POSTPONE
------------------------

Do not spend hackathon time on:
- User authentication.
- A database covering every plant species.
- A complex RAG pipeline unless there is a clear, tested need.
- Training/fine-tuning a model from scratch.
- Chat history.
- A full weather dashboard.
- Large-scale data collection.

These can be useful later, but the first goal is to prove this workflow:
PHOTO -> VISUAL EVIDENCE -> PLAUSIBLE ASSESSMENT -> ACTIONABLE CARE REPORT.

-------------------
